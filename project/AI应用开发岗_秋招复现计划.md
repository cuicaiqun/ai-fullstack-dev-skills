# AI 应用开发岗 · 秋招项目复现计划

> 面向：零基础 / 初学者，准备秋招 **AI 应用开发** 岗位  
> 目标：把本项目吃透到「可演示、可讲述、经得起追问」，而不是 1:1 搬空仓库  
> 相关文档：[学习建议.md](./学习建议.md) · [问题清单.md](./问题清单.md) · [ROADMAP.md](./ROADMAP.md)

---

## 1. 核心结论

**值得动手复现，但不要从零完整复刻整个 monorepo。**

| 判断 | 结论 |
|------|------|
| 要不要动手复现？ | **要**。动手是掌握项目、应对追问最有效的方式 |
| 要不要从零 1:1 复刻整仓？ | **不要**。投入产出比差，容易陷入环境与基建泥潭 |
| 最佳策略 | **最小可用 RAG → 深挖 2～3 个亮点 → 准备讲述与追问** |
| 成功标准 | 不是「代码和原项目一样」，而是「闭卷画出架构并扛住追问」 |

一句话：

> 用「面试可用的深度复现」，代替「仓库级完整搬迁」。

---

## 2. 为什么这个想法方向是对的

面试官很少只听「我看过 RAG / LangGraph」，更看重：

- 能不能讲清一条完整链路
- 有没有亲手踩过坑、做过权衡
- 出了问题如何排查与降级

本项目天然适合练这些能力，尤其是三条主链路：

```text
1. 文档入库：上传 → 解析 → 分块 → 知识抽取 → 向量库 / 图谱
2. 问    答：问题 → 向量检索 + 图谱检索 → 重排序 → LLM 回答
3. 文档更新：变更事件 → CDC 处理 → 删除旧知识 → 写入新知识
```

更细的分层学习方法见 [学习建议.md](./学习建议.md)。

---

## 3. 零基础「全量复现」的风险

本项目不是入门 demo，而是偏工程化的 AI 应用，涉及：

- FastAPI + LangGraph Agent
- 向量库 / Neo4j
- Kafka / Watchdog / CDC
- 多租户、鉴权、部署、测试门禁

若零基础且坚持「环境到每一行都自己重写」，常见结果是：

1. 2～3 周仍在配置 Docker / Neo4j / Kafka
2. 代码抄完了，却讲不清「为什么这样设计」
3. 秋招时间被基建吃掉，算法 / 八股 / 项目表达都没练够

**面试要的是可讲述的深度，不是仓库复刻完成度。**

另外注意：`ROADMAP.md` 中有「已实现 / 部分实现 / 设计目标 / 尚未验证」的区分。  
**不要把文档里的设计描述，直接当成全部已经完成的功能。**

## 4. AI 应用开发岗：面试官真正想听什么

高频追问通常覆盖这 6 块：

1. **RAG 全链路**：解析 → 分块 → embedding → 检索 → 重排 → 生成 → 引用
2. **编排**：为什么用 LangGraph / Agent，状态怎么传，失败怎么重试
3. **检索质量**：纯向量不够时怎么办（混合检索、图谱、rerank、grounding）
4. **数据更新**：文档改了如何增量同步（CDC、幂等、一致性）
5. **工程化**：FastAPI 接口、异步、鉴权 / 多租户、可观测、降级
6. **取舍**：为什么这样设计，不用会怎样，挂了怎么办

### 4.1 优先吃透的代码位置

| 模块 | 路径 | 作用 |
|------|------|------|
| API 入口 | `code/python/api/main.py` | HTTP 接口、参数校验、调用工作流 |
| 编排 | `code/python/orchestrator/graph.py` | LangGraph 入库 / 问答 / 更新图 |
| Agent | `code/python/agents/` | 解析、抽取、QA、知识更新 |
| 向量检索 | `code/python/services/vector_store.py` | 向量写入与检索 |
| GraphRAG | `code/python/services/graph_rag.py` | 图谱增强检索 |
| 重排 | `code/python/services/rerank.py` | 粗召回后的精排 |
| Grounding | `code/python/services/grounding.py` | 降低幻觉、可追溯 |
| CDC | `code/python/services/cdc_processor.py` | 变更事件处理 |
| 状态 | `code/python/services/state_store.py` | 文档状态 / 检索门禁等 |
| 配置 | `code/python/config/settings.py` | 环境与依赖配置 |

### 4.2 主链路（先记住这张图）

```text
用户请求
  ↓
FastAPI 接口（code/python/api/main.py）
  ↓
LangGraph 工作流（code/python/orchestrator/graph.py）
  ↓
Agent（code/python/agents/）
  ↓
向量库 / Neo4j / Kafka 等服务（code/python/services/）
```

## 5. 推荐策略：分阶段复现（不要一次做完）

### Phase 0：先讲清楚（1～2 天）

**不写业务代码，先能口述：**

- 用户是谁，解决什么问题
- 三条主流程分别怎么走
- 每步对应哪个模块（API / Graph / Agent / Store）
- 哪些是已实现，哪些只是设计目标

**完成标准：** 能画一张图连续讲 5 分钟，不看代码。

### Phase 1：最小可运行版（最值得复现，1～2 周）

只做一条能跑通、能演示的链路：

- 文档上传 / 加载
- 分块 + embedding + 向量检索
- FastAPI 问答接口
- 简单引用 / 来源返回

**完成标准：** 本地能 demo，并能讲清每个环节为什么需要。  
→ 这是简历上的 **MVP 演示**。

### Phase 2：加 2～3 个「面试闪光点」（再 1～2 周）

不要全做，选你能讲透的：

| 候选亮点 | 你要能讲到的点 |
|----------|----------------|
| LangGraph 工作流 | 节点、状态、失败重试 |
| 图谱 / 混合检索 | 为什么比纯向量更稳 |
| CDC / 增量更新 | 为什么不能每次全量重建、如何幂等 |
| 多租户 / 权限 | 为什么检索必须带 tenant 过滤 |
| Rerank | 粗召回 + 精排 |
| Grounding | 如何降低幻觉、`grounded=false` 何时出现 |

原则：**少而深**。每个点都能回答：

- 为什么这样做
- 怎么做的
- 失败怎么办
- 如何验证

建议优先组合：**Rerank + Grounding**（最好讲，也最好演示）。  
图谱 / Kafka 有余力再加。

### Phase 3：工程化（有余力再做）

测试、Docker、降级、观测、部署。  
有当然加分，但不应压过 Phase 1 / 2。

## 6. 复现时如何学，才经得起追问

每做一个模块，强制写 4 句话（面试就靠这个）：

1. **是什么**
2. **为什么需要**
3. **我怎么实现的**（关键类 / 函数即可）
4. **如果挂了会怎样 / 我如何验证**

### 示例：CDC

不要只说「用了 Kafka」，而要说：

> 核心是只处理变更，而不是全量重建；事件如何标识与幂等；重复消费会怎样；失败如何重试或进 DLQ；与全量重建相比的取舍和代价。

### 示例：问答接口

不要只说「用了 FastAPI」，而要说：

```text
POST /api/qa/ask
输入：question、session_id、history
处理：鉴权 → 调用 QA 工作流 → 检索 / 重排 / 生成
输出：answer、confidence、sources
```

请求从哪进、参数在哪校验、调用了谁、经过哪些模块、最终返回什么。

## 7. 十四天执行计划（秋招版）

> 假设每天可投入约 2～4 小时。可按实际时间整体平移，但不要打乱阶段顺序。

### 总原则

- 每天产出：**1 个可演示点 + 1 段面试口述稿**
- 代码可以参考本项目，但关键路径必须自己重写一遍
- 每完成一块，写清：是什么 / 为什么 / 怎么做 / 挂了怎么办

### 每日节奏（建议）

| 比例 | 内容 |
|------|------|
| 40% | 读本项目对应模块（只读相关文件，不散读） |
| 40% | 自己写最小实现 |
| 20% | 写面试口述稿 + 至少 3 个追问答案 |

---

### Day 1～2：业务地图 + 最小骨架

**做什么**

- 画出三条链路：入库 / 问答 / 更新
- 搭最小项目：`FastAPI + /health + /api/qa/ask`（可先 mock 返回）
- 读懂 `QuestionRequest` / `QuestionResponse`、鉴权依赖大致位置

**面试能讲**

- 系统解决什么问题
- 为什么 API 层和 Agent 层要拆开
- 为什么问答常用 `POST` 而不是 `GET`

**完成标准**

- 能 5 分钟画图讲完，不看代码

---

### Day 3～5：RAG 最小闭环（最重要）

**做什么**

- 文档加载 + 分块
- embedding + 向量库写入 / 检索（Chroma 即可）
- `ask`：检索 topK → 拼 prompt → 调 LLM → 返回 answer + sources

**刻意追问自己**

- chunk size / overlap 怎么定
- topK 太大 / 太小会怎样
- 没有命中文档时怎么答（拒答 vs 瞎编）
- 如何返回可追溯 sources

**完成标准**

- 本地上传 1～2 篇文档，能问出带引用的答案
- 这是你简历上的 MVP 演示

---

### Day 6～7：LangGraph 编排 + Agent 边界

**做什么**

- 把「直接函数调用」改成图：
  - 入库：`parse → extract → store_vectors (→ store_graph)`
  - 问答：至少 `retrieve → (rerank) → generate`
- 对照 `orchestrator/graph.py`，理解节点输入 / 输出状态

**面试能讲**

- 不用图、直接写 if-else 有什么问题
- 状态里该放什么、不该放什么
- 某节点失败如何重试 / 降级，而不是整条链路崩掉

**完成标准**

- 能指着自己的 graph 说明每个 node 的职责

---

### Day 8～9：检索增强（只选 2 个深挖）

从下表选 **2 个** 做成亮点，不要贪多：

| 亮点 | 你要能讲到的点 |
|------|----------------|
| **Rerank** | 粗召回 + 精排，为什么比只靠向量距离稳 |
| **GraphRAG** | 实体 / 关系如何帮助「多跳 / 关系类」问题 |
| **Grounding** | 如何降低幻觉、什么时候 `grounded=false` |
| **混合检索思路** | 语义检索的边界；何时需要关键词 / 过滤条件 |

**优先推荐：** Rerank + Grounding。

**完成标准**

- 准备 3 组对比题：有 / 无 rerank、有 / 无 grounding 的效果差异

---

### Day 10～11：文档更新 / CDC 思维（差异化点）

**做什么**

- 实现「文档更新」最小版：
  - 识别新增 / 修改 / 删除
  - 删旧 chunk / 向量，再写新数据
  - 用 `event_id` 做幂等，避免重复消费
- 对照 `cdc_processor.py`、`knowledge_update_agent.py`
- Kafka / Watchdog 先理解职责，第一周不必强上集群

**面试能讲**

- 为什么不能每次全量重建
- 幂等是什么，重复事件会怎样
- 向量库和图谱一致性怎么保证（至少能讲策略和当前缺口）

**完成标准**

- 改一份文档后，问答结果会更新
- 重复触发不会把数据写炸

---

### Day 12：工程化薄切片（够用就行）

只做面试常问的一层：

- 基本鉴权（登录后拿 token 再问答）
- 租户 / 用户隔离意识（检索必须带过滤条件）
- `health`、基础日志、关键路径错误返回
- 1～2 个核心单测：检索过滤 / 幂等更新

**面试能讲**

- 服务挂了如何降级（向量库挂、LLM 挂）
- 为什么不能「检索不加 tenant 条件」

---

### Day 13：简历叙事 + 追问题库

#### STAR 叙事模板

- **场景（S）**：企业知识库文档多、更新频繁、不能瞎编
- **任务（T）**：做可引用、可更新的 RAG 问答
- **行动（A）**：分块策略、Graph 编排、rerank / grounding、增量更新
- **结果（R）**：用你真实测到的例子（时延、命中、更新生效）说话

#### 简历表述示例

> 基于 FastAPI + LangGraph 实现企业知识库问答：支持文档解析分块、向量检索、重排序与引用返回答案；设计文档变更后的增量更新与幂等处理，避免全量重建；补充基础鉴权与健康检查，完成本地可演示闭环。

#### 建议自备的追问（示例）

- 分块太大 / 太小分别会怎样？你如何选？
- topK 如何调？调大后延迟和噪声如何平衡？
- 幻觉怎么抑制？拒答策略是什么？
- 为什么引入 Agent / Graph，而不是一条直线脚本？
- 文档更新如何保证幂等与一致性？
- 向量库挂了、LLM 挂了，分别怎么降级？
- 如何评估效果（正确率 / 引用率 / 拒答率）？
- 本项目里哪些是已实现，哪些还只是设计？

可把个性化问题持续记入 [问题清单.md](./问题清单.md)。

---

### Day 14：模拟面试（只练表达）

按下面结构讲 **8～10 分钟**：

1. 业务问题（约 1 min）
2. 架构图与三条链路（约 3 min）
3. 深挖 1 个技术点：RAG 质量 **或** CDC（约 3 min）
4. 权衡与不足（约 2 min）

然后接受约 20 分钟追问。  
讲不清的点记下来回去补，**不要再扩需求。**

## 8. 复现范围：必须掌握 vs 可延后

| 必须掌握 | 可延后 |
|----------|--------|
| FastAPI 问答 / 上传主链路 | 完整前端企业工作台 |
| 向量 RAG 闭环 | 生产级 Kafka 集群 |
| LangGraph 基础编排 | K8s / 完整可观测平台 |
| 增量更新 + 幂等思路 | 多模态全量能力 |
| Rerank 或 Grounding 至少其一 | ROADMAP 中全部企业验收项 |
| 基本鉴权与隔离意识 | 完整 TLS / 密钥轮换演练 |

**最终成功标准（一句话）：**

> 关掉代码，你仍能画出架构，并独立讲清「RAG 质量」与「文档更新」两个深挖点。

## 9. 学习时的纪律清单

1. **先地图，后细节**：说不清链路时，不要钻进某个依赖的配置项。
2. **先 MVP，后亮点**：没有可演示问答前，不上 Kafka / 多租户大全套。
3. **少而深**：亮点 2～3 个讲透，好过 10 个名词浅尝。
4. **区分现状**：已实现 / 部分实现 / 设计目标 / 未验证，面试里主动说清。
5. **每天留口述**：能跑不等于能讲；能讲才算面试资产。
6. **问题进清单**：把追问记入 [问题清单.md](./问题清单.md)，带着自己的立场去验证。

## 10. 建议的本地练习目录（可选）

若希望「自己复现一份」而不污染本仓库业务代码，可在仓库外或 `project/` 下自建练习目录，例如：

```text
my_rag_interview/
├── README.md                 # 你的架构说明 + 口述稿
├── app/
│   ├── main.py               # FastAPI 入口
│   ├── graphs/               # LangGraph 编排
│   ├── agents/               # 解析 / QA / 更新
│   ├── services/             # 向量库、rerank、cdc
│   └── models/               # 请求响应模型
├── data/                     # 示例文档
├── tests/                    # 少量核心测试
└── notes/
    ├── architecture.md       # 架构图与三条链路
    ├── decisions.md          # 设计取舍
    └── interview_qa.md       # 追问与回答
```

本仓库中：

- **规则与 Skills**：仓库根目录 `skills/`、`templates/`（不要往里面写真实业务代码）
- **真实业务项目**：`project/` 下的 `code/python/` 等
