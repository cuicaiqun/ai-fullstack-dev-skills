# 项目学习与问题分层建议

这个项目内容较多，不建议一开始就试图弄懂所有技术。更有效的方法是先建立“项目地图”，再按层次记录问题。已有的 [问题清单.md](问题清单.md) 可以继续作为问题记录入口。

## 一、先记住项目主链路

```text
用户请求
  ↓
FastAPI 接口（code/python/api/main.py）
  ↓
LangGraph 工作流（code/python/orchestrator/graph.py）
  ↓
Agent
  ↓
向量库 / Neo4j / Kafka 等服务
```

项目主要包含三条流程：

```text
文档入库：上传 → 解析 → 分块 → 知识抽取 → 向量库/图谱
问答：问题 → 向量检索 + 图谱检索 → 重排序 → LLM 回答
文档更新：变更事件 → CDC 处理 → 删除旧知识 → 写入新知识
```

主要代码位置：

- FastAPI：`code/python/api/main.py`
- 工作流：`code/python/orchestrator/graph.py`
- Agent：`code/python/agents/`
- 服务：`code/python/services/`
- 配置：`code/python/config/settings.py`

## 二、建议按六个层次整理问题

### 1. 业务层：系统解决什么问题？

先回答：

- 用户是谁？
- 用户上传文档后，系统做了什么？
- 用户提问时，系统如何找到答案？
- 文档修改后，知识库如何同步？
- 为什么不能每次都全量重建？

这一层重点是讲清楚“为什么做”，暂时不要陷入代码细节。

### 2. 架构层：模块如何协作？

画出三条主流程，并标注每一步对应的代码文件。这样比单独背 FastAPI、Kafka、Neo4j 的定义更容易理解整体系统。

### 3. 接口层：FastAPI 做什么？

可以这样理解：

> FastAPI 是系统对外提供服务的入口层。它接收 HTTP 请求、校验参数、调用内部工作流，并把结果转换成 JSON 返回。

建议整理这些问题：

- 一个接口由哪些部分组成：路径、HTTP 方法、请求体、响应体、状态码？
- 为什么上传文档使用 `POST`？问答接口为什么通常也使用 `POST`？
- `Pydantic BaseModel` 如何做参数校验？
- `async def` 带来了什么好处？
- `lifespan` 启动时初始化了哪些依赖？
- 如果 Neo4j 或向量库不可用，接口是否仍能启动？

以问答接口为例，应追踪：

```text
POST /api/qa/ask
输入：question、session_id、history
处理：调用 QA 工作流
输出：answer、confidence、sources
```

不要只写“用了 FastAPI”，而要写清楚：请求进入哪里、参数在哪里校验、调用了哪个函数、经过哪些模块、最终返回什么。

### 4. 数据处理层：CDC 是什么？

CDC（Change Data Capture）的核心不是 Kafka，而是：

> 只处理发生变化的数据，而不是重新处理所有数据。

本项目的逻辑可以概括为：

```text
文件修改 / Kafka 事件
        ↓
统一成 CDCEvent
        ↓
判断 INSERT / UPDATE / DELETE
        ↓
计算 before 和 after 的差异
        ↓
调用 KnowledgeUpdateAgent
        ↓
更新向量库和知识图谱
```

关键文件：

- `code/python/services/cdc_processor.py`
- `code/python/agents/knowledge_update_agent.py`
- `code/python/services/state_store.py`

重点问题：

- `CDCEvent` 统一了哪些字段？
- 如何判断文档是新增、修改还是删除？
- `compute_diff()` 如何计算变化比例？
- 为什么需要 `event_id`？
- 什么是幂等？重复收到同一个事件会怎样？
- 失败后如何重试？
- 版本号保存在哪里？

要区分以下几种情况：

```text
已实现
部分实现
设计目标
尚未验证
```

项目的 [ROADMAP.md](ROADMAP.md) 已指出，CDC 虽然已经接线，但生产级一致性和端到端验证仍存在缺口。不要把文档中的设计描述直接当成全部已经完成的功能。

### 5. 基础设施层：Watchdog 和 Kafka 做什么？

- Watchdog：监视本地文件夹，文件发生变化时通知程序。
- Kafka：可靠的事件传递系统，生产者发送消息，消费者异步处理。

两者不是同一个东西：

| 项目 | Watchdog | Kafka |
|---|---|---|
| 监听对象 | 本地文件系统 | 消息流或数据库变更事件 |
| 作用范围 | 通常是单机 | 可跨进程、跨机器 |
| 消息持久化 | 通常不负责 | 支持保存和重放 |
| 适合场景 | 本地目录自动更新 | 分布式系统异步消费 |
| 本项目位置 | `KnowledgeUpdateAgent.start_watching()` | `CDCProcessor.start_kafka_consumer()` |

继续追问：文件连续保存会不会触发多次事件？Kafka 消费失败会不会丢消息？什么是 offset、consumer group、手动 commit 和死信队列？两条路径同时运行会不会重复更新？

### 6. 可靠性与运维层

最后再整理：

- 服务启动失败怎么办？
- 外部存储不可用时如何降级？
- 重复请求如何保证幂等？
- Kafka 消费失败如何重试或进入 DLQ？
- 服务重启后版本和事件状态是否保留？
- 哪些功能有测试，哪些只有设计没有 E2E 验证？

## 三、每个问题使用固定模板

```markdown
## Q：为什么本项目需要 CDC？

### 1. 现象
文档修改后，知识库需要自动同步。

### 2. 我的理解
以前可能是定期扫描所有文件，现在只处理发生变化的文件。

### 3. 涉及概念
CDC、事件驱动、幂等、消息队列、增量更新。

### 4. 代码入口
- services/cdc_processor.py
- agents/knowledge_update_agent.py
- api/main.py 的 lifespan

### 5. 实际流程
文件事件/Kafka 消息
→ CDCEvent
→ process_event()
→ process_change()
→ 更新向量库和图谱

### 6. 已确认事实
根据代码，事件会生成 event_id，并支持幂等处理。

### 7. 尚未确认
compute_diff() 的结果是否真正决定了局部更新范围？

### 8. 风险与改进
需要测试重复事件、消费失败、服务重启后的恢复。
```

## 四、推荐学习顺序

1. 阅读 `项目介绍/项目整体文档...md`，了解系统目标。
2. 阅读 `项目介绍/文件树描述...md`，建立文件和模块的对应关系。
3. 跟踪一条完整的文档入库调用链，从 `POST /api/ingest/upload` 开始。
4. 跟踪一条完整的问答调用链，从 `POST /api/qa/ask` 开始。
5. 最后学习 CDC：`Watchdog/Kafka → CDCProcessor → KnowledgeUpdateAgent`。
6. 每看一个模块，都补一张“输入—处理—输出—异常”的小表。

## 五、写文档时的原则

- 不要把项目介绍中的描述直接当成事实，要回到代码验证。
- 明确区分“已实现”和“设计目标”。
- 一个问题只讨论一个核心概念。
- 先写自己的理解，再写代码证据。
- 每个问题最后补一句“我还不会什么”。
- 优先记录数据流和调用关系，而不是堆砌术语。
